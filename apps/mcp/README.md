# Optional portable MCP server

`server.py` exposes the existing IC Workbench tools and four MCP App resources through the official `modelcontextprotocol/python-sdk`. It is a tool/resource transport adapter, not a chat service, model runtime or replacement engineering executor. Existing `Service`, `ViewService`, `ReviewSession` and optional `PluginRuntime` keep their responsibilities.

The existing Python 3.9 zero-dependency plugin and CLI are unchanged. This optional entry uses a separate **Python 3.11+** environment. Backend file locking and stdio transport now support macOS, Linux, and native Windows via `ic_gateway.platform_compat` (validated by `.github/workflows/cross-platform-ci.yml`). The resolved lockfile was generated on macOS arm64 Python **3.12.14** and includes all official non-yanked platform wheel hashes at each pinned version.

## Dependencies and provenance

- Official SDK: **`mcp==2.3.0`**, stable release dated **2026-10-02**, **MIT** license.
- Sources: <https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.3.0> and <https://pypi.org/project/mcp/2.3.0/>.
- SDK wheel SHA-256: `dd0c44c089d16453e8ae31a3877a0054d7a2314caaa81f5e0541b9b1734b2377`.
- `requirements.lock` pins all 28 resolved packages and official wheel hashes; source builds are disabled. It includes all non-yanked wheel hashes at each selected version for platform portability, but that does not constitute cross-platform execution validation.
- `dependency-provenance.json` records package licenses, required Python ranges, PyPI metadata URLs and the installed wheel hashes. Transitive package licenses remain their respective licenses; MIT refers to the MCP SDK.
- `refresh_lock.py` is an explicit maintainer utility, never invoked by normal startup or builds.

The SDK installs some HTTP/auth dependencies even though this adapter only serves stdio. No HTTP listener, OAuth flow, public endpoint, credential acquisition or model connection is configured here.

## Provision once, then let the MCP host start it

The integrator provisions an isolated environment, not the user's global Python or current plugin environment:

```sh
python3.12 -m venv /absolute/ic-mcp-venv
/absolute/ic-mcp-venv/bin/python -m pip install --require-hashes -r /absolute/apps/mcp/requirements.lock
```

Configure the agent's MCP server command once. Each session then launches and owns the stdio subprocess automatically; users do not start a Python daemon in a separate terminal.

Example generic host configuration, with paths filled by the integrator:

```json
{
  "mcpServers": {
    "ic-workbench-portable": {
      "command": "/absolute/ic-mcp-venv/bin/python",
      "args": ["-B", "/absolute/apps/mcp/server.py", "--settings", "/absolute/settings.json"]
    }
  }
}
```

This is a generic host launch example, not a change to the installed Codex plugin's portable manifest. Use the selected host's own configuration format.

Exactly one input is required:

- `--settings /absolute/settings.json`: reuses existing `PluginRuntime`. Catalog/initialize/resources do not start the gateway; a workbench tool lazily reuses or starts the already configured local backend. Exposes status/connect tools. This mode has 31 tools in the current backend.
- `--config /absolute/client.json`: reuses an existing `Service` client configuration and its externally managed gateway. It does not auto-start or replace a gateway and has 29 tools in the current backend.

No launch configuration is generated by this module and no production settings are modified. Missing settings can be diagnosed through `ic_plugin_status`; conflicts and denied operations retain the existing behavior.

## Source and package layout

From source, the adapter resolves `../../apps/codex` and `../../modules/gateway_client` relative to itself. In the optional built package it resolves adjacent `backend/icwb` and `backend/lib/ic_gateway`:

```text
dist/ic-workbench-mcp/
  server.py
  strict_input.py
  smoke.py
  requirements.lock
  backend/
    icwb/
    lib/ic_gateway/
    ui/
    gateway/
```

The root build owns packaging. Engineering data, state, private configuration and the dependency virtualenv do not belong in the package.

## Review boundary

Tool schemas and annotations are copied from the existing backend, including app-only UI tool metadata. Tool result `structuredContent`, `isError`, text content and `_meta.icWorkbench.data` are preserved; UI resource MIME and `_meta` remain intact. App-only metadata is not authentication or approval.

`ic_request_review` accepts only request ID and fingerprint. The adapter uses the existing `ReviewSession` to produce the complete frozen review and form, then the SDK sends a server-originated elicitation and owns the actual wire request ID. Only the awaited matching host response is forwarded to that review's internal correlation ID. Raw response values are retained for strict boolean and extra-field checks; a value like `1` is not promoted to approval.

Before the SDK's typed decoder, `strict_input.py` validates the original UTF-8 JSON bytes through the transport's public stdin hook. It rejects duplicate keys at any depth (including escaped equivalent keys), nonfinite numbers and exponent overflow, invalid UTF-8/surrogates, invalid IDs and extra/conflicting response-envelope fields. Valid lines pass unchanged. Frames are limited to 2 MiB; oversized input is drained in bounded chunks without exposing fragments to the SDK. Invalid frames are dropped and logged without their contents. Because a malformed frame has no trusted identity, it cancels any currently waiting review through the SDK's pending request await and keeps the receipt pending; even a subsequent valid reply to that retired wire ID cannot approve. No replacement reply, decision or correlation ID is generated by the input gate. Other valid traffic can continue; review is never automatically restarted.

One review is active at a time per stdio process. Other reads remain responsive while the human decides. Cancellation, missing form capability, timeout, host rejection and invalid responses do not approve and do not schedule retries. Existing receipt locks and durable dispatch state prevent automatic replay. The default review deadline is 120 seconds; configure the host tool timeout above that, e.g. 180 seconds. Only the connected host may obtain a human decision; MCP does not cryptographically prove human presence.

The validated initialization protocol is **2025-11-25**. Existing review support also understands **2025-06-18**. If a newer SDK protocol era is negotiated without the existing ReviewSession recognizing it, review fails closed as unsupported. Modern protocol authentication/claim semantics are not implemented here. A plain MCP host may call tools/read resources without supporting MCP App rendering; no UI mounting claim follows from a resource response.

Multiple agents using the same state directory share **one user's trust domain**. This is not per-agent authorization or isolated state. Do not expose this stdio adapter or the local gateway to untrusted clients or public networks.

## Smoke and tests

`smoke.py` uses the official `ClientSession` and launches the specified server process. With no project it only initializes/lists/status-checks. With explicit project/run it reads the project registry, persisted job catalog and saved results; it never requests review, creates a UI view, prepares a mutation, samples a model, or submits/collects/publishes a simulation.

```sh
/absolute/ic-mcp-venv/bin/python apps/mcp/smoke.py --config /absolute/client.json
/absolute/ic-mcp-venv/bin/python apps/mcp/smoke.py --server /absolute/dist/ic-workbench-mcp/server.py --config /absolute/client.json --project PROJECT --run SAVED_RUN
/absolute/ic-mcp-venv/bin/python -B -m unittest discover -s tests/mcp -p 'test_*.py' -v
```

Python interface: `await smoke.probe(server_path, config=path, project_id=..., run_id=...)`, or `settings=path` instead of `config`.

Test fixtures use a synthetic service/host, never live approvals or simulations. Real stdio subprocess tests verify official client initialization/list/read/call, schema and metadata parity, review failure behavior, cancellation, no replay, and stdout purity including process shutdown. Real project/waveform acceptance, target-agent installation and native UI mounting remain separate integration checks.
